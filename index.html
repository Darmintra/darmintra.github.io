System prompt disclosure in a production LLM agent

A public-sector AI assistant returned its complete system prompt in response to a plain conversational question — no jailbreak, no obfuscation, no technical knowledge required. A second phrasing, asking the agent to summarise its own context, produced the same disclosure, indicating the model had no notion that its instructions were meant to be confidential.

The interesting part was not the extraction but the impact analysis. A leaked system prompt hands an attacker the map to every guardrail the agent has. In this case it also exposed two things the operator had not intended to publish:

  • A third-party vendor relationship the prompt explicitly instructed the agent never to mention
  • Internal platform architecture — document handling, citation structure, and internal identifier formats

My recommendations went beyond the single agent: audit every agent on the platform with the same extraction prompt to establish whether the issue was systemic, filter known extraction patterns at the platform layer rather than per-agent, and treat the prompt layer as non-confidential by design — no vendor names, no secrets, nothing that cannot survive disclosure.

Another researcher had reported the same issue first, so the report was closed as a duplicate.

Client-supplied identifier in a national-identity password reset flow

A password reset flow authenticated by a national digital identity service also accepted a client-supplied account identifier in the request body. If the server derived the target account from that value rather than from the authenticated identity, any authenticated user could reset another user's password.

I could not prove it either way without testing against an account I did not own, which the programme rules prohibited. Rather than test anyway, I documented the attack chain, said plainly that my proof of concept only demonstrated self-context, and asked the security team for either a test account or an internal code review.

They provided a test account. I ran the cross-account test and the server rejected it — the identifier is validated against the authenticated identity server-side. I reported that my own finding was wrong and the report was closed accordingly.

One design observation survives the negative result. The identifier does not need to be in the client request at all: the server already holds the authenticated identity and can resolve the account internally. Leaving it client-controlled means correctness now depends on a validation check that must never regress — a single-layer defence where no layer was necessary. Sound implementation, avoidable design surface.
