Duplicate · independently identified

System prompt disclosure in a production LLM agent

A public-sector AI assistant returned its complete system prompt in response to a plain conversational question. No jailbreak, no obfuscation, no technical knowledge required. A second phrasing, asking the agent to summarise its own context, produced the same disclosure, which told me the model had no notion its instructions were meant to be confidential.

The extraction was trivial. What mattered was the impact analysis. A leaked system prompt hands an attacker the map to every guardrail the agent has, and in this case it also exposed two things the operator had not meant to publish:

  • A third-party vendor relationship that the prompt explicitly instructed the agent never to mention
  • Internal platform architecture, including document handling, citation structure, and internal identifier formats

My recommendations went past the single agent. Audit every agent on the platform with the same extraction prompt to establish whether the issue was systemic. Filter known extraction patterns at the platform layer rather than agent by agent. And treat the prompt layer as non-confidential by design, so that no vendor name, secret, or anything else that cannot survive disclosure ever sits in it.

Another researcher had reported the same issue first, so the report closed as a duplicate.

Not exploitable · control confirmed effective

Client-supplied identifier in a national-identity password reset flow

A password reset flow authenticated by a national digital identity service also accepted a client-supplied account identifier in the request body. If the server derived the target account from that value rather than from the authenticated identity, any authenticated user could reset another user's password.

I could not prove it either way without testing against an account I did not own, and the programme rules prohibited that. Rather than test anyway, I documented the attack chain, said plainly that my proof of concept only demonstrated self-context, and asked the security team for either a test account or an internal code review.

They provided a test account. I ran the cross-account test and the server rejected it, because the identifier is validated against the authenticated identity server-side. I reported that my own finding was wrong and the report closed accordingly.

One design observation survives the negative result. The identifier does not need to be in the client request at all, since the server already holds the authenticated identity and can resolve the account internally. Leaving it client-controlled means correctness depends on a validation check that must never regress, which is a single layer of defence in a place that needed no layer at all. The implementation is sound. The design surface is avoidable.
